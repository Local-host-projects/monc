SPENDING THAT
CAN ONLY SAY YES

MONC lets an owner delegate payment without handing over unlimited trust. A merchant or an AI agent proposes one exact transaction. The owner reviews it, proves ownership from their own device, and MONC settles it — but only if every condition can be confirmed from a authoritative source, right now.

The one tenetMINIMIZE INPUT · COLLECT FROM THE SOURCE
Design ruleMinimize data entry from both parties and collect directly from the sources in the most definitive / authoritative way.

Neither the customer nor the merchant should have to type facts that a trusted system already holds. The customer never types the merchant's name or city. The merchant never types the customer's details. MONC pulls each condition from the record that is authoritative for it:

  • Amount, currency, product, category, domain — from the payment intent ledger, written by the merchant's own API and never typed by the customer at checkout.
  • Merchant identity and city — re-checked live at the bank (account enquiry / branch record) at authorization time, not trusted from an onboarding form.
  • Consent — polled live from the bank during the consent hop; MONC never imagines an approval.

The verification harness below is the machine that runs those checks. Every check carries its source and a timestamp, and anything that can't be confirmed fails closed — no authorization, no settlement.

How a payment movesCHECK · CONSENT · SETTLE
  1. 1 · ProposalThe merchant sends an exact payment intent: fixed amount, product, domain.
  2. 2 · Ownership proofThe owner decrypts their token from their own device and signs the exact transaction context — the private key never leaves the browser.
  3. 3 · Live verificationEvery policy condition is re-checked from its authoritative source right now.
  4. 4 · PolicyThe owner's compiled rules decide yes or no. Anything unverifiable fails closed.
  5. 5 · ConsentALAT Authenticator gets the exact debit for approval; MONC polls the bank.
  6. 6 · SettlementWema credits the merchant wallet; the ledger records it once, idempotently.
Running the harnessVERIFY IN REAL TIME

The same pipeline the checkout uses is exposed as a tool:

In the appThe Account console verifies your instruments and rules before they are used. The checkout shows you each live check and where the value came from.
From the APIGET /api/verify/sources lists the authoritative source map. POST /api/verify/run runs the checks for a payment intent (or a sandbox sample) and returns per-condition verdicts with provenance.
From the terminalpython scripts/verify_harness.py prints the report. python scripts/verify_harness.py --fail-source proves that a source outage fails closed instead of authorizing.
Prototype boundaryDEMO MODE

This deployment runs in sandbox mode: Wema calls are deterministic and in-memory, and card details are encrypted in this browser — never test with a real card. In production the gateway uses live Wema / ALAT credentials, a PCI tokenization provider, and server-side key management. The verification harness and fail-closed rules are exactly the same code path.
